# 适配新模型

## 核心原则

先固定模型契约和 Oracle，再复用仓库已有能力完成端到端接入。**默认完整适配包括适用的权重精度、CPU/GPU 和 CLI/HTTP；开工前列覆盖矩阵，交付时逐项留证。** 数值按预先校准的指标验收，逐位比较用于定位分叉；GPU 路径按同机参考实现给出性能对标。

## 范围与覆盖矩阵（开工前必填）

只有用户明确限定范围（例如“仅 CPU CLI 原型”）时，才缩减交付目标；记录该约定，无需反复确认。只拿到一种权重、只在本机有 CPU、某入口接起来容易，都不是缩减实现范围的依据。

从目标架构兼容的转换器、loader、共享算子和同类模型确定**应支持**的格式与能力，不能反过来用新模型当前已写好的代码定义范围。先列出每种格式和组件的具体名称，再将每个适用的「能力/组件 × 权重格式 × 后端」组合逐行填写；CLI、HTTP 必须分别留证：

| 能力/组件 | 权重格式 | 计算/KV 精度 | 请求后端 | CLI 命令与结果 | HTTP 路由、请求与结果 | 实际执行后端、数值指标与证据 | 实现/验证状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |

状态分两列写：实现状态「已实现 / 未实现 / 不适用」，验证状态「通过 / 失败 / 未运行」。不适用项要有契约或仓库能力依据；缺实现、缺权重、缺硬件都要保留条目和原因，不能写成不适用或通过。**已实现但未运行的项仍不能称为已验证。**

「未实现」分两类，处理方式不同：

- **本次交付内可继续补齐的** → 继续补齐，不得留到下一层；
- **依赖仓库内仍在发展的共享能力**（Vulkan 算子、设备调度等）→ 允许留空，但必须写明具体缺口（哪个算子 / 哪条路径）、为什么本次无法自足、以及后续 owner 与层号。

允许留空不等于可以静默：这类条目在矩阵里保持「未实现」，在交付结论里体现为「部分适配（共享能力待补）」，不能写成「不适用」或「完整适配」。

| 维度 | 必须覆盖 |
| --- | --- |
| 权重精度 | 逐项核对适用的 F32、F16、BF16 以及仓库已支持的 Q8、Q4/K/IQ 等具体导出格式；不为凑表新增无关量化算法。转换器能导出不代表 loader、CPU kernel、GPU kernel 都能运行。权重存储类型、实际计算/累加精度、KV 类型分开记录，不能用「转成 F32 后能跑」宣称原生低精度加速。**转换脚本本身也是交付物**：至少覆盖仓库已有的量化导出能力（Q8_0 / Q4_K 等），只导出 F32 应记为未实现项。 |
| CPU | 正常推理走共享算子的 SIMD/线程池，覆盖 prefill、decode 或该模型对应阶段；标量路径只作参考或既有 fallback，不把手写标量 Oracle 翻译当生产实现。 |
| GPU | 补齐该能力的仓库现有设备路径，分别验证 `cpu`、`auto`、严格设备模式（当前为 `vulkan`）。保留实际 backend、设备提交/算子执行证据，逐项对照 CPU 数值；混合执行写清 CPU/GPU 分工。白名单、设备可见、编译通过或 Auto 回退 CPU 均不是 GPU 支持证据。 |
| 入口 | 同一能力同时接入 CLI 和按能力命名的 HTTP 路由，共用 `models/` 实现；覆盖架构注册、backend 构造、参数/请求校验、输出及错误映射。已有 HTTP 路由不代表新架构已接通。若该能力有流式/非流式接口，两条都验证；无需为本不支持流式的能力新增协议。 |
| 能力/组件 | 按实际模型契约列出文本、视觉、音频、embedding、rerank 等任务及所需 encoder、projector、decoder/head；校验组件匹配和缺失错误。JEV 对具备对应概率/评分语义的模型检查文本及适用媒体，并比较 CLI/HTTP 结果；不强加给纯 TTS/图像生成等无此语义的模型。 |

没有 GPU 硬件时，先补齐可实现的设备路径、能力门禁与检查，再标记「已实现 / 未运行」；没有 kernel 或设备调度时是「未实现」，不能以没硬件掩盖。优先使用已有可用且已授权的本机/测试机；本 skill 不授权租用云机器，AMD Cloud 仍仅在用户明确要求时使用。

## 分层交付

包过大时可以拆成多层 PR。每层 PR 覆盖矩阵的一部分，交付时逐行写明「本层已覆盖 / 其余层待合入（层号 + 计划）」。分层 PR 不因剩余条目未完成而被判失败，但必须：

- 列出剩余层的范围、内容与合入顺序；
- 已合入的层不得留下「未实现且无计划」的条目；
- 只有全部层合入后，模型才能标「适配完成」；单层合入时标「部分适配（分层交付中）」。

分层的依据是工作量，不是范围缩水：分层只切分工作量，不切分应支持的范围。每层要覆盖自己负责的那几行组合（精度 × 后端 × 入口），不能用「这一层只做 CPU」来缩小整体应支持的格式集合。

## 硬约束

- 不得新增、调用或建议接入任何外部加速库，包括 OpenBLAS、BLAS/LAPACK、MKL、Apple Accelerate、oneDNN、cuBLAS、rocBLAS。只能使用仓库已有的 Rust 算子、线程池、SIMD、量化内核和现有依赖；能力不足时报告阻塞，不得绕过限制。
- 不得把未知架构默认路由到相近模型。只有 Tokenizer、张量契约、位置编码、归一化、Attention/KV、FFN/MoE 和输出变换均一致时才能复用实现，并且仍需显式注册新架构。
- 将用户指定的 llama.cpp 或官方实现视为只读 Oracle。需要插桩时，在临时副本中固定 commit 后修改，不污染用户的参考仓库。
- 以实际模型契约和提供的 GGUF、mmproj、组件确定任务能力；没有多模态组件就不扩展多模态支持。只提供某一精度的权重不等于用户只要求这一精度，缺少验证资产要单独列出。
- **模型适配不得擅自改变编译产物集合。** 除非用户明确要求独立可执行文件，否则接入现有
  `rust-model-inference` / `rust-model-server` 的参数与调度，不新增 `src/bin/<model>.rs`
  或 `[[bin]]`。Cargo 会自动发现 `src/bin/*.rs`，未改 Cargo.toml 也会增加产物；
  不得靠修改 `default-run`、关闭 `autobins` 或 feature gate 掩盖这个问题。
- **入口层按能力抽象，不按模型名堆文件。** 模型级 CLI 编排层放在 `src/app/<model>.rs`
  是允许的（`MODEL_ORGANIZATION.md` §9 P-4 的迁移目标就是 `src/app/gemma4.rs`），
  但它成立的前提是「这个入口形态只服务一个模型」。当第二个同形态的模型接入、
  你正要复制上一份同名文件时，就把入口抽成通用的一份，模型差异下沉到
  `src/models/<model>/`；入口层最终只做编排，不含模型分支。
  判定与检查项见仓库 `.agents/skills/reviewing-model-changes/SKILL.md` 的「命名红线」。

## 改动边界：新模型局部化

- **默认保持其他模型的专属实现不变。** 新模型的配置、权重组合、cache/session 和 forward 差异放在自身 `src/models/<model>/`，优先组合已有算子与稳定接口；确需扩展 Qwen3 等已有模型的专属结构时，必须先说明为什么在 `src/models/<model>/` 内组合已有算子与稳定接口不能满足，并保持旧模型的默认配置与推理路径不变，不要为了少写几行而塞入模型专属字段、状态枚举或条件分支。
- 本规范不追溯判定已经合入的改动；本规范生效后的新改动才按上面的口径审。
- 必要的架构注册、公共入口接线和真正共享的能力扩展可以修改；开工前列出「新模型 / 必要注册 / 共享设施 / 其他模型专属代码」的改动清单。判断共享性看实际调用方与契约，不只看目录名；某模型目录内已被多个模型使用的公共设施，仍按共享代码审查。
- 差异仅属于新模型时，保留少量局部 glue/适配结构，复用底层计算；不复制整个已有模型，也不顺手重构、搬迁或改名其他模型。相同行为的入口抽象规则不授权重写其他模型内部结构。
- **确需跨模型修改时，逐处说明必要性**：具体共享缺陷或接口缺口是什么，为什么新模型局部实现不能满足；只扩展最小公共能力，保持既有 API、默认配置和执行语义。新模型特有行为应显式 opt-in，不能改变旧模型默认路径。
- 修改共享设施或其他模型前，用 CodeGraph 追踪全部调用方，保存受影响旧模型的当次基线；改后对照相关入口、精度/后端和数值结果。编译或构造单测不能替代旧模型真实推理回归。缺少旧模型验证资产时优先选可行的局部方案；确实无法避免的改动明确标为未验证，不声称旧模型已回归通过。

## 工作流

1. **固定输入与范围**：记录模型路径、SHA256、文件大小、量化类型，读取 `general.architecture`、相关 metadata、Tokenizer/chat template 和张量名称/shape/type、组件清单，填写上述矩阵。取权重按仓库 `.agents/skills/model-download/SKILL.md` 的渠道优先级走（ModelScope 优先 → HF；HF 连不上时试 `HF_ENDPOINT=https://hf-mirror.com`，仍校验 SHA256 与 revision）。
2. **固定 Oracle**：优先检查用户点名的本地参考仓库，确认其 commit、工作区状态、模型实现、Tokenizer 和转换脚本确实支持目标架构。找不到匹配 Oracle 时停止并说明缺口，不猜测实现。
3. **追踪完整路径**：结构查询优先使用 CodeGraph；定位转换/量化、架构注册、Tokenizer、张量加载/类型分发、模型构造、forward/session、CPU/GPU 算子与能力门禁、CLI 调度、HTTP backend/路由、适用的 JEV、`parity-trace` 和相邻测试。列出需同步的调用方、测试/fixture、配置/导出和文档，先比较契约再复用。用 `cargo metadata --locked --no-deps --format-version 1` 记录二进制 targets 的名称和路径，完成后与基线比较，确认没有意外新增或移除编译产物。
4. **先写失败检查**：覆盖显式架构分发、metadata/shape/组件错误、Tokenizer 的特殊 token/Unicode/空白与 Oracle 一致；为每条新精度/后端分支留下小型行为测试，并检查 CLI 与 HTTP 确实进入新路径。不支持的格式、KV/设备组合在两入口均明确拒绝，严格设备模式不得静默降级。
5. **实现矩阵中的路径**：补齐配置、Tokenizer、权重映射与类型分发、模型计算/状态、设备调度及两条入口。模型语义放 `models/`，CLI/HTTP 只编排；复用仓库算子，遵循仓库 `.agents/skills/operator-internal-dispatch/SKILL.md`，不为未来模型建立抽象层。不可用的既有格式/后端要修根因，不能简单加白名单或将其删出矩阵。**默认用仓库自己的算子（`dot_f32`、`softmax_inplace`、`silu_inplace` 等），不要因为「参考实现是这么算的」就照搬 ggml 的累加结构** —— 浮点加法不满足结合律，换累加顺序只是换一种舍入，ggml 的结构既不是精度最优也不是速度最优。只有命中「无法绕开的精度问题 / 行为对齐问题 / 行为对齐测试 / 精确数值测试」四种情况之一时，才引入 `_ggml` 后缀的函数，并在注释里写明为什么绕不开。详见 `operator-internal-dispatch` skill 的「`_ggml` 后缀函数的使用边界」。
6. **数值对齐**：使用下节的固定 Oracle 和分精度指标；出现差异定位首个分叉 checkpoint，不以可读文本代替数值证据，也不为了逐位一致永久关闭 SIMD/GPU。
7. **验证真实入口与回归**：按矩阵运行 release 或仓库约定的验证构建、真实 CLI、启动 server 后的实际 HTTP 请求；每种适用格式与后端组合均要有推理记录，不能以 mock、构造成功或通用路由测试替代。验证 Auto 的真实设备执行及无设备/不支持组合的 CPU fallback，严格设备模式则明确报错。适用时按「性能对标」测同机 CPU / Vulkan / 参考实现的耗时。共享算子改动检查所有调用方；相关测试与格式/编译检查需执行，历史失败、环境失败、本次回归分开报告。
8. **同步文档和状态**：更新 `docs/MODEL_LIST.md`、`docs/develop/SUPPORTED_MODELS.md` 及 `tools/oracle/<model>/README.md`、`validation.md`，记录契约 pin、矩阵、命令、日期/主机、阈值与实测指标，以及性能对比与差距归因。备注按仓库 `reviewing-model-changes` 的 √ 约定填写；缺必要入口/精度/后端或未验完时标「待核验 / Experimental / 部分适配」，不得无条件打 √。

## 数值验收与排障

- 固定模型/revision、Oracle commit、输入与预处理、Tokenizer/template、seed/greedy、线程、计算/KV 精度；分别验证 prefill 和多步 decode，非文本模型使用对应中间结果与任务输出。Tokenizer、shape、特殊 token 等离散契约必须精确一致。
- **每种权重精度单独对齐**：优先用同一量化文件/语义的 Oracle；官方不能直接加载该 GGUF 时，用同一权重的独立反量化/等价参考路径，写明限制。同时将量化相对全精度的质量损失与实现误差分开；只有 F32 Oracle 记录不能证明量化路径正确。
- 对浮点、SIMD、GPU、量化使用适合任务的 max_abs、RMSE/相对误差、cosine 及输出质量指标；阈值须在验收前依据参考精度、已有校准样例确定，不能看到失败后放宽。报告实测值及阈值，生成模型另比较多步 greedy/token 分歧；分歧要定位、解释并验证任务质量，不能只凭文本可读通过。
- 需要定位差异时比较 checkpoint 顺序/shape/次数和首个分叉，必要时临时关闭 SIMD/FMA/近似计算并对可比中间值做 `to_bits()` 比较。**跨框架或 lossy 路径不以逐位一致为通用前置门槛**；用户明确要求 bit-exact 的路径必须遵守，达不到时如实报告。

## 性能对标

Vulkan 路径的验收除数值外还要给性能参考。同一台机器、同一权重精度、同一输入长度与 batch 下，报告 CPU / Vulkan / 参考实现（PyTorch 官方实现或 llama.cpp）的墙钟时间或 tok/s，并写明差距归因（哪个算子回退 CPU、哪个 kernel 未实现）。

- 性能是**参考基线，不是硬门槛**：Vulkan 算子仍在发展中，落后于 PyTorch 是可接受的，但不允许没有数字；
- 参考实现的数字必须来自**同一机器实测**，不得引用官方 README 或他人机器的数字；
- 没有 GPU 硬件时写「已实现 / 未运行」，并给出 CPU 实测值与预期的 GPU 路径；
- 记录位置：`tools/oracle/<model>/performance.json` 与 `docs/develop/<MODEL>.md`。

## 完成定义

| 层级 | 必须提供的证据 |
| --- | --- |
| 模型契约 | GGUF 哈希、架构、关键 metadata、张量名称/shape/type |
| Tokenizer | 输入文本及双方完全相同的 token IDs |
| 数值/任务 | 每种精度的 Oracle、指标/阈值、实测结果、多步或任务输出对比；有差异时提供首个分叉及解释 |
| 覆盖矩阵 | 每种适用格式 × CPU/Auto/设备的实现与验证状态，CLI/HTTP 各自命令、真实后端、结果和证据路径；适用 JEV/流式同样留证 |
| 性能 | 适用时给出同机 CPU / Vulkan / 参考实现的耗时或吞吐对比与差距归因；无 GPU 硬件时写「未运行」并给出 CPU 实测 |
| 改动边界 | 新模型、必要注册、共享设施及其他模型改动清单；每处跨模型改动的必要性、受影响调用方和旧模型基线/回归结果 |
| 工程/文档 | 实际执行的检查、共享调用方回归、模型清单和 Oracle 复现记录 |
| 遗留项 | 未实现、失败、未运行、不适用项及原因，对应用户范围约定或验证限制 |

**只有用户约定范围内的必要项均已实现且验证通过，才能称为「适配完成」。** 明确拒绝不支持的请求是错误处理通过，不等于该精度/后端已支持；写出限制也不能替代补齐可继续实现的缺口。环境/资产确实阻塞，或所依赖的共享算子/设备路径仍在仓库内发展中时，可交付部分结果，必须标明「部分适配（已实现未验证）」或「部分适配（共享能力待补）」，并写明剩余步骤与具体缺口。

## 最小示例

若 `newarch` 的家族转换器支持 F16、Q8_0、Q4_K_M，而目前只有 F16 CPU CLI 跑通，应继续补另外两种格式、GPU 路径及 HTTP 注册/真实请求。Auto 的 `backend=CPU, submission=0` 只证明回退可用；严格 Vulkan 返回不支持也不算 GPU 适配。记录每个组合的结果后再判断交付状态。

## 常见错误

- 只看模型名称，不检查 GGUF metadata 和张量清单。
- 选用了"附近"的 llama.cpp checkout，而不是实际支持该架构的固定版本。
- 只比较最终文本，遗漏 Tokenizer、prefill、KV 续写或中间层差异。
- 为追求速度先接入 OpenBLAS 等外部库，改变浮点顺序并掩盖正确性问题。
- 把仓库原有编译故障算作适配回归，或把未运行的真实模型检查写成已通过。
- 「只给了 F32」「没 GPU」「HTTP 已有通用路由」：分别检查格式实现范围、真实设备路径、新架构注册与实际请求；红旗是矩阵里没有这些条目。
- 「不支持时能报错就算做完」「写清限制即可」：只证明错误处理；必要支持仍缺失时继续实现，不能改成不适用或完整适配——除非该缺口属于「共享能力待补」并已写明具体缺口与后续计划。
- 手写 PyTorch ATEN kernel 的标量翻译版本（polynomial exp 近似、分层 multi-lane dot product、4-level sum-of-squares），而非复用 `crate::ops::` 已有 SIMD 算子。这些手写版本在 Rust 中无法被编译器向量化，性能和可维护性都更差。典型反例：82 行手写 sum-of-squares 替代 1 行 `iter().map().sum()`；49 行闭包 dot product 替代 `crate::ops::dot_f32`。
