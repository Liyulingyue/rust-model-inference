# 审阅模型改动

## 核心原则

审阅的目标不是「代码能跑」，而是**这条改动在所有真实入口上都不会给出错误答案**。
适配类改动最容易出的问题不是编译错误，而是**某个入口静默走了另一条路**：新 arch 落进
旧模型的白名单、只改了 CLI 没改 HTTP、Auto 与 CPU 的输出差一个 token、共享算子的
一个分支改动悄悄影响了另外三个调用方。

## 分层红线：models 实现模型，app 只是输入接口

| 层 | 放什么 | 不放什么 |
| --- | --- | --- |
| `src/models/<model>/` | 模型契约、权重映射、计算图、位置编码、Tokenizer 行为、模型级管线（forward / session / decoder） | CLI 参数、HTTP 路由、文件读写 |
| `src/app/` | 输入接口：CLI 参数解析、请求装载、输出序列化、进程编排 | 模型计算逻辑 |
| `src/app/server/` | HTTP 路由与 handler，按**能力**命名 | 模型计算逻辑（应 `use crate::models::…`） |

判定方法：**这段代码换一个入口（CLI ↔ HTTP）还要不要用？** 要用 → 属于 `models/`；
只有某个入口用 → 属于 `app/`。

具体症状（审阅时逐条查）：

- `src/models/<model>/` 里出现 `CliOptions` 之外的 app 层编排（允许引用 `app::cli` 的
  **类型**与纯函数，如 `KvFormat`；不允许引用入口编排）；
- `src/app/` 里出现模型计算循环（forward / session / 解码器调用）→ 应下沉到 `models/`；
- server handler 从 `crate::app::` 拿模型语义 → 应改成 `crate::models::`；
- `src/models/hybrid.rs` 这类「按 arch 分发」的清单缺新 arch；
- 模型名出现在**通用**结构里（如 server 的通用 `TextBackend` 挂 `xxx_decoder` 字段）
  → 应当给该模型专属 `Backend` 变体 + 专属 backend struct。

### 命名红线

- `src/app/server/` 下的文件与路由按**能力**命名（`forecast.rs` → `/v1/forecast`，
  `rerank.rs` → `/v1/rerank`），**不按模型名**；
- 模型专属能力要有**专属 `Backend` 变体**，路由只挂在自己的变体上；
  通用后端不得为某个模型开专用字段；
- `src/models/<model>/` 的目录名、`general.architecture`、转换器目录名三者一致。

## 五条必查覆盖矩阵

审阅任何模型适配/重构，逐条给出**证据**（命令 + 输出），没有证据的条目按「未验证」写，
不得默认通过。

### ① CLI / HTTP / JEV 三条入口

| 入口 | 必查 |
| --- | --- |
| CLI | 模型专属参数是否生效；与其它任务模式是否互斥；无效组合是否**明确报错**而不是被静默忽略 |
| HTTP | 路由是否只挂在本模型该有的 backend 上；错误码语义（400 / 404 / 429 / 501）是否与实际能力一致 |
| JEV | 图像 JEV 与文本 JEV 都要跑；CLI 与 HTTP 的概率是否一致 |

**最常见的洞：某个 flag 只在一条入口生效。** 例如「只给 `--mmproj`、没有媒体」时，
CLI 会掉进另一条分支，而 server 走的是完全不同的分派——两条都试一遍。

### ② CPU SIMD 加速

- 新算子是否走 `crate::ops::` 的既有 SIMD 入口，而不是手写标量
  （见 `operator-internal-dispatch` skill）；
- 标量与 SIMD 的归约顺序不同 → 测试用容差而非 bit-exact，但**结论里要写明**；
- 若本次改动落在**共享算子**上：逐个列出所有调用方，并**证明**每个调用方的行为是
  变好了、还是逐位不变。判断依据是「三轴位置是否全等」这类真实前提，不是「看起来无关」。

### ③ 多权重分发

- 一个 GGUF 里多套权重（text / mmproj / 额外 head / decoder）时：
  - 每个组件的 arch、张量契约、量化类型是否都被校验；
  - 组件缺失是否给出**指名道姓**的错误（缺哪个、为什么需要）；
  - 组件与主模型**不匹配**时是否在启动/请求时被拒（而不是拿错组件跑出一堆噪声）。
- 同一模型多档量化：至少覆盖仓库支持的每种导出类型，报告**逐档**差异
  （token IDs 是否一致、坐标/数值偏差量级），不要只测一种。

### ④ CPU↔GPU 自动分发

`ComputePolicy` 有三档，审阅时逐档看：

| 档位 | 必查 |
| --- | --- |
| `cpu` | 参考输出（其它档位与它对比） |
| `auto` | 真的落到设备了吗（看 `backend=Vulkan` 与 submission 计数，不要只看「有 GPU」）；设备缺失时回退 CPU；输出与 CPU 是否一致 |
| `vulkan` | 请求了严格设备路径而模型不支持时，是**明确报错**还是静默降级 |

两条硬规则：

- **白名单不是能力证明**。`has_complete_device_path()` 只决定「要不要打印 warning」，
  不代表该 arch 的设备路径与 CPU 对齐；实测过才算。
- **warning 不能是唯一的告知**。校验层放行之后，运行时仍要有能力门禁给出真实原因
  （例如「需要 F16 KV」「该 arch 无完整设备路径」），否则用户只看到一句 warning。

### ⑤ 共享算子 / 共享配置的影响面

改动落在共享代码（`src/ops/`、`src/models/qwen3/trunk/`、`src/app/text/`）上时，
必须逐个调用方证明影响。特别注意**非穷尽模式**：

- `match` 的 arm 是编译器保证的；**`if let` / `matches!` 改了 enum 变体不会报错**，
  只会静默走 else 分支 → 改 `enum` 后第一件事是 grep 所有 `if let Backend::…`；
- 位置编码 / 词表 / 归一化这类「实现细节」要**对着官方源码逐槽核对**，
  不要凭直觉（例如 M-RoPE 的轴分配要逐槽比对官方 `apply_interleaved_mrope`）。

## 文档三件套必须同步

代码行为变了，这三处要一起改，否则文档会开始骗人：

| 文件 | 内容 |
| --- | --- |
| `docs/MODEL_LIST.md` | 型号、arch、已验证格式、验证范围、已知限制 |
| `docs/develop/SUPPORTED_MODELS.md` | 同上 + 复现入口链接 |
| `tools/oracle/<model>/README.md` + `validation.md` | 契约 pin、复现命令、**实测记录**（含日期与主机） |

已过时的结论要**更正**而不是删掉——写清「原结论是什么、为什么被推翻、新结论的实测
依据是什么」。同时检查代码里的注释：注释里写死的行为（错误信息、启动日志、CLI usage）
也是对外契约。

## 回归验证纪律

- 先拿**当次基线**：`cargo test --locked --lib` 的 passed/failed/ignored 与**失败名单**；
  改动后再跑，逐条对比名单。只比总数会漏掉「新增一个失败 + 少一个失败」的抵消。
- 历史失败、环境失败、本次回归**分开报告**；没跑过的检查不得写成通过。
- 涉及数值的改动，**用两个独立 host/配置交叉验证**：CPU 与 Auto、量化与非量化、
  同一模型的不同尺寸——本机一次「恰好没翻」不能当结论。
- 数值不稳定的场景（多线程归约、边界翻转）要**多跑几次**再下结论；
  greedy 输出不稳定本身就是要报告的事实。

## 完成定义

一份审阅结论至少包含：

1. **分层检查**：`models/` 与 `app/` 的职责是否干净，有无模型名泄漏到通用层；
2. **五条矩阵**：CLI / HTTP / JEV、CPU SIMD、多权重分发、CPU↔GPU 自动分发、
   共享算子影响面——每条给出证据或「未验证 + 为什么」；
3. **文档同步**：三件套是否与代码一致；
4. **回归**：基线对比结果；
5. **发现清单**：按严重度排序，每条给出 `file:line`、复现方式和建议修法；
   区分「必须改」「建议改」「需要上游确认」。
