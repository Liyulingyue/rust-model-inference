# Qwen-Drive-1.0-4B Native GGUF Support Design

## Goal

Add native Qwen-Drive-1.0-4B support to `rust-model-inference`, export the supplied Hugging Face checkpoints to source-precision GGUF components, and validate each component against a fixed reference implementation.

The scope includes all released components:

- the shared Qwen3.5-4B VLM for text and image VQA;
- the SFT and RL planning experts;
- the perception head for 3D detection, occupancy, and BEV map segmentation.

The implementation must remain pure Rust at runtime and must not add or call external acceleration libraries. The existing repository operators, thread pool, SIMD, quantized kernels, and dependencies remain the only runtime foundation.

## Fixed Oracles

- Qwen3.5 text and vision: local llama.cpp checkout at `b96806d96061049a5b574269b049bf6241d63d46`. Oracle instrumentation is applied only to a temporary clone. Existing repository scalar softmax and scalar K-quant patches are reused.
- Qwen-Drive planning and perception: official `QwenLM/Qwen-Drive-1.0` source at `28091c1532e869bc7aee91fc0aef6b3e6fd0b2e0`. Instrumentation and CPU-only reference substitutions live only in a temporary clone.

Python and PyTorch used by the official Oracle remain isolated validation dependencies and are not added to the repository or Rust runtime. Exact-parity fixtures disable fused and nondeterministic backends and use fixed scalar accumulation order; optimized Oracle output is not accepted as a substitute for the scalar reference.

The official perception path uses CUDA 12.8 and custom BF16 CUDA kernels. The current Apple M3 Max host cannot run that final Oracle. The accepted local completion boundary is native implementation plus deterministic CPU operator and component validation. End-to-end bitwise comparison with the official CUDA perception pipeline remains a named NVIDIA validation gate and must not be reported as passed locally.

## Artifact Layout

Export five independent files next to the source model:

1. `Qwen-Drive-1.0-4B-BF16.gguf`: Qwen3.5 text trunk, `general.architecture=qwen35`.
2. `Qwen-Drive-1.0-4B-mmproj-BF16.gguf`: Qwen3.5 vision tower and merger using the metadata and tensor contract already consumed by `models::qwen35::vision`.
3. `Qwen-Drive-1.0-planner-sft-BF16.gguf`: `general.architecture=qwen_drive_planner`.
4. `Qwen-Drive-1.0-planner-rl-BF16.gguf`: `general.architecture=qwen_drive_planner`.
5. `Qwen-Drive-1.0-perception-F32.gguf`: `general.architecture=qwen_drive_perception`.

Source precision is preserved. This first adapter does not create Q8 or other quantized variants: conversion accuracy and parity come first, and the host has only about 27 GiB free before export. The exporter streams tensor payloads, writes through an atomic temporary file, validates metadata and tensor payload digests, then installs one completed output before starting the next. It never materializes a second full checkpoint in memory and refuses to overwrite an existing artifact unless explicitly requested.

## Conversion

A repository-local Qwen-Drive converter reads safetensors headers and streams payloads using the existing exporter machinery.

- VLM conversion strips the outer `vlm.` prefix and reuses the pinned llama.cpp Qwen3.5 text and vision mappings. It must not teach the generic converter that `qwen_drive` is an alias for Qwen3.5; the wrapper is explicit because the external heads make the top-level architecture different.
- Planner conversion strips `planning_expert.` and maps each released tensor to a stable `qwen_drive_planner.*` GGUF name. Both SFT and RL use the same schema and differ only in payload hashes.
- Perception conversion strips `bev_modeling.` and maps the released FPN, depth, view-transform, BEV encoder/decoder, detection, occupancy, and map tensors to a stable `qwen_drive_perception.*` schema.

Conversion tests use small synthetic safetensors fixtures. They prove prefix handling, tensor completeness, exact shapes and dtypes, source-to-output byte preservation, metadata validation, atomic output behavior, and rejection of unknown or missing tensors.

## Runtime Architecture

### Shared VLM

No new language-model graph is introduced. VQA and all shared feature extraction use the existing `qwen35` tokenizer, multimodal preprocessing, vision encoder, mRoPE position builder, text trunk, session, and CLI path.

The Qwen-Drive layer adds only the taps required by the official model:

- post-rotary keys and values from zero-based full-attention layers 3, 7, 11, 15, 19, 23, 27, and 31 for planning;
- vision features immediately before the patch merger and final-normalized language image-token features for perception.

These taps are opt-in outputs. Normal Qwen3.5 inference retains its current allocations and behavior.

### Planning Expert

`models::qwen_drive::planning` implements the released 32-layer planning expert:

- history, velocity, acceleration, navigation, ego state, waypoint index, Fourier waypoint features, and sinusoidal flow-time encoders;
- per-layer AdaLN modulation;
- gated grouped-query joint attention over the VLM cache and 50 waypoint tokens;
- SwiGLU FFN;
- interleaved partial mRoPE anchored immediately after the VLM prefix;
- ten-step default Euler integration of the clean-endpoint flow field;
- the released normalization constants, BF16 rounding behavior, noise seed, and heading wrap.

Four consecutive planner layers consume one of the eight VLM full-attention caches: zero-based planner group `i` consumes VLM layer `4i + 3`. SFT and RL are the same runtime architecture and are selected only by which planner GGUF is loaded.

### Perception Head

`models::qwen_drive::perception` implements the released fixed-resolution pipeline:

1. VLM pre-merge and post-norm image feature taps.
2. The LLM and ViT FPN branches.
3. Depth prediction and frustum unprojection.
4. Deterministic voxel pooling into the fixed 200x200x16 volume.
5. BEVFormer encoder and detection decoder with deformable attention.
6. Detection, occupancy refinement, and map segmentation heads.
7. Post-processing into boxes, scores, labels, occupancy classes, and map classes.

Only inference operations are implemented. Training, backward kernels, distributed evaluation, visualization, and CUDA-specific fast paths are out of scope. Perception-specific convolution, normalization, grid sampling, scatter, and deformable-attention code stays inside the Qwen-Drive module unless an existing repository primitive already has the exact required semantics.

## CLI and Data Flow

VQA keeps the existing interface:

```text
rust-model-inference --model <vlm.gguf> --mmproj <mmproj.gguf> \
  --image <image> --prompt <question>
```

Planning follows the official JSONL scene contract and directory-backed images:

```text
rust-model-inference --model <vlm.gguf> --mmproj <mmproj.gguf> \
  --planner <planner.gguf> --scenes <scenes.jsonl> --image-root <dir> \
  --mode direct_planning|reasoning_planning --num-samples <n> \
  --num-steps <n> --seed <n> --output <predictions.jsonl>
```

The first version deliberately omits Parquet image archives, sharding, resume support, and benchmark evaluators. Directory-backed images cover inference and exact fixtures; those operational features can be added independently if needed.

Perception follows the official frame-directory concept:

```text
rust-model-inference --model <vlm.gguf> --mmproj <mmproj.gguf> \
  --perception <perception.gguf> --frames <frame-dir> --output <result.json>
```

The frame manifest contains camera order, image paths, image shapes, dataset type, and calibration matrices. Fixture preparation in the temporary Oracle environment converts the official demo's NPZ calibration file into this JSON manifest; the repository and Rust runtime gain no NumPy/NPZ dependency. The result JSON contains boxes, scores, labels, occupancy shape and byte values, and map shape and byte values.

CLI validation rejects incompatible or incomplete combinations before loading multi-gigabyte weights. New head files require the matching explicit architecture and required metadata. Qwen-Drive paths never use an unknown-architecture fallback.

## Validation

Development follows red-green TDD. Each non-trivial branch or parser gets the smallest runnable regression test before implementation.

Every parity trace has a checked-in manifest fixing checkpoint names, order, shapes, occurrence counts, and deterministic value ranges. Reduced operator fixtures compare every F32 word. Full-model traces compare whole-tensor SHA256 values computed over little-endian F32 `u32` words; a mismatch reports the first differing element and both raw `u32` values. Tolerances, cosine similarity, and readable output are never parity evidence.

### VLM

- Export readback: GGUF metadata, tokenizer, tensor names, shapes, types, and payload digests.
- Tokenizer fixtures: BOS/EOS, ChatML special tokens, Unicode combining marks, whitespace, and image placeholders.
- Text parity against pinned llama.cpp: identical token IDs, checkpoint order/shapes/counts, full checkpoint bit digests, final logits bits, and multi-step greedy tokens.
- Vision parity against an instrumented pinned llama.cpp multimodal Oracle: identical resized image bytes/patches, image token IDs and grids, vision checkpoints, merged embeddings, text checkpoints, logits bits, and greedy tokens.

### Planner

- Configuration and weight-shape rejection tests.
- Exact fixtures for Fourier features, time embedding, history normalization, mRoPE, QKV split/gates, AdaLN, joint attention, FFN, Euler updates, heading wrapping, and deterministic noise.
- An official PyTorch CPU Oracle test for each released planner using identical synthetic VLM caches and scene tensors. Compare checkpoint sequence, shapes, occurrence counts, every manifest-specified F32 bit pattern, and final 50x3 trajectory bits.
- Real CLI runs for both direct and reasoning planning on a fixed official scene fixture. The reasoning path also verifies VLM greedy tokens.

### Perception

- Exact small fixtures for convolution, normalization, FPN resampling, bilinear grid sampling, deformable attention, frustum projection, voxel grouping/accumulation order, and post-processing.
- Official PyTorch CPU references cover every operator expressible without custom CUDA. For CUDA-only operators, the temporary Oracle supplies scalar implementations, including voxel pooling with the published CUDA loop order.
- Component checkpoint order, shape, occurrence, raw F32 words, and deterministic post-processed class outputs on reduced fixtures.
- A required real native CLI run on one official demo frame; report elapsed time, peak memory, and output shapes. If it cannot finish on the current host, local completion is blocked rather than silently downgrading this check.
- Deferred NVIDIA gate: same frame, source weights, BF16 CUDA kernels, and checkpoint filters against official commit `28091c1532e869bc7aee91fc0aef6b3e6fd0b2e0`. Until this runs, documentation must say that full CUDA end-to-end parity is unverified.

### Engineering Checks

- focused exporter and Rust unit/integration tests;
- `cargo fmt --check`;
- `cargo check` and release build for the actual CLI;
- source-precision artifact readback and SHA256;
- real VQA, planner SFT, planner RL, and perception commands;
- documentation updates in `docs/MODEL_LIST.md` and `docs/develop/SUPPORTED_MODELS.md` with exact coverage and the CUDA limitation.

Baseline or environment failures are reported separately from regressions. No unrun check is described as passing.

## Explicit Non-Goals

- training or fine-tuning;
- CUDA, Metal, Vulkan, BLAS, or other new acceleration support for the added heads;
- quantized planner or perception artifacts;
- Parquet archives, multi-GPU sharding, resume logic, benchmark scoring, or visualization;
- claiming official CUDA perception parity from CPU-only evidence.

## Completion Criteria

The task is locally complete when all five GGUF artifacts exist and pass readback, the VLM and both planners satisfy their stated exact-parity gates, the perception module passes deterministic component validation and a real native entry-point run, focused engineering checks pass, and the documentation accurately marks the deferred CUDA perception gate. Full end-to-end perception parity remains incomplete until that NVIDIA gate runs.
